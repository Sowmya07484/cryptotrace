01 · The Problem

Why this system needs to exist

Fraud victims report a crypto wallet address — but the address alone tells investigators nothing. It has no name attached.

Who reports what

Victims of investment scams, task-based fraud, sextortion, ransomware, phishing, darknet deals, and organized cyber-financial crime report the wallet the scammer used.

Why it's hard

Reported wallets are usually non-custodial, burner, or intermediary — designed to have zero identity attached, and often moved across multi-chain transfers, DeFi, mixers, bridges, and privacy tech.

What's actually needed

Find the nearest exchange (VASP) the funds reached — because that's the only point where a real identity (KYC) was ever collected.

Why a wallet has no identity, but an exchange does

Wallet address

Just a self-generated cryptographic key pair. Anyone creates one instantly, for free, with no ID, no form, no company involved. No database anywhere links it to a real person.

Exchange (VASP) account

A regulated company account. Legally required to collect KYC (ID proof) before letting anyone deposit or withdraw. This is the only point in the entire chain where a real identity was ever recorded.

This single fact is the whole logic of the system: trace the money until it touches an exchange, because that's the only link that can ever be turned into a real name.

What's automatic vs. what needs a legal process

StageNeeds formal legal process?
Reading blockchain data, tracing hopsNo — public data, no subpoena needed
Identifying which exchange received fundsNo — public data + labelling
Getting who owns that exchange accountYes — formal request to the exchange (SAHYOG / PMLA)
Freezing the fundsYes — formal request / court order

Our system's job ends at the top two rows — fast, automated, evidence-backed. A human investigator handles the legal steps below, using what our system hands them.

Full PS requirement checklist

  • Ingest wallet addresses reported through cybercrime complaint systems (NCRP).
  • Automatically trace the blockchain and identify the associated exchange/VASP.
  • Detect fund movement patterns and generate actionable intelligence.
  • Analyze transaction graphs, cluster exchange wallets, detect intermediary/laundering wallets.
  • Track cross-chain movement — funds jumping between blockchains via bridges.
  • Integrate with SAHYOG (freeze/info requests) and NCRP (complaint intake).
  • Generate alerts and categorize wallets by risk.
  • Support multiple blockchains, in real time, with an investigator-facing dashboard.
  • Produce standardized investigation reports usable as evidence.
  • Use AI/ML to assist risk detection and recognize fraud typologies automatically.

03 · Vocabulary

Terms everyone on the team must know

If you can't explain these in one sentence, a judge's follow-up question will catch you off guard.

Blockchain

A public, permanent transaction ledger anyone can read — no login or subpoena needed to look up an address.

Wallet address

A free, self-generated key pair. Zero identity attached — this is the entire reason tracing is hard.

VASP

Virtual Asset Service Provider — a regulated exchange legally required to do KYC. The only place identity exists on-chain.

Non-custodial / burner wallet

User-controlled or disposable wallets, used specifically to break the money trail.

Hop / hop-by-hop tracing

Following funds one transfer at a time, wallet to wallet, until they hit something recognizable.

Mixer (e.g. Tornado Cash)

Pools many users' funds to break the sender–receiver link. A genuine, honest dead end — even for commercial tools.

Bridge

Moves assets across blockchains — tracing must switch chains and continue on the other side.

Clustering

Grouping many addresses as one real owner using behavioral patterns (e.g. common-input-ownership).

OFAC / SDN list

US Treasury office; its sanctions list includes officially designated wallet addresses — a legally authoritative red flag.

Layering

Rapid multi-hop movement to obscure the origin of funds — the crypto version of money-laundering "smurfing."

04 · System Overview

What we're actually building

One input, one clear output — everything else supports this single loop.

  • Input: a wallet address (from a victim complaint, or typed in for the demo).
  • Trace: pull the wallet's real transactions live and follow the largest transfer, hop by hop.
  • Check: at each hop, check the address against a known-entity label database.
  • Flag: if no label matches, check for suspicious behavioral patterns (fan-in/fan-out) instead of giving up.
  • Verdict: Matched exchange (actionable) / Hit sanctioned mixer (trail cold) / Flagged pattern or no match (manual review).

06 · Recurring Pattern Detection

Matching new wallets to known fraud patterns

Beyond checking if an address is already known-bad, we compare a newly traced wallet's behavior against fraud fingerprints extracted from real, labelled datasets — catching typology matches even on wallets nobody has seen before.

  • Step 1: extract behavioral features (time-to-outflow, fan-in/fan-out ratio, hop depth to exchange, transaction size pattern) from known fraud addresses in Real-CATS (103,203 real criminal + 106,196 benign addresses) and Elliptic++.
  • Step 2: compute the same features for the newly traced wallet.
  • Step 3: score similarity against known typology fingerprints (Ponzi, phishing, ransomware payout, etc.) — even a simple weighted-rule or cosine-similarity match works.
  • Step 4: output a typology label with a confidence score, e.g. "78% match to known phishing-payout pattern" — explainable, not a black-box AI claim.

This directly satisfies the PS's "automated pattern recognition for fraud typologies" requirement using real, citable, labelled data rather than an unproven model.

07 · Behavioral Heuristics

Catching wallets that aren't in any label list

Most real-world addresses will never be in any label database. These heuristics let the system flag likely-exchange or likely-laundering wallets even when nothing is labelled — this is what "detection of intermediary laundering wallets" actually means in practice.

Fan-in / fan-out pattern

Many inbound senders followed by rapid outbound splitting is a classic layering signature; ordinary personal wallets rarely behave this way.

Time-to-outflow

Funds that leave within minutes to a couple of hours of arriving are far more likely to be in active laundering than sitting in genuine savings.

No balance accumulation

A wallet that always passes funds straight through, never holding a balance, behaves unlike a normal user wallet.

Common-input-ownership clustering

Addresses used together as inputs in one transaction usually share a real owner — this is how GraphSense itself grows its label database.

A wallet that trips several of these heuristics gets flagged "suspicious pattern detected — recommend manual review" instead of a flat, uninformative "no match found."

08 · Report Triage

Prioritizing which complaints to work first

With a high volume of NCRP complaints, investigators can't act on all of them at once. The system ranks incoming reports so the most time-sensitive, highest-value, and most-connected cases surface first.

Ranking factorWhy it matters
Fund traceability statusFunds still sitting in a traceable wallet are worth acting on now; funds already at a mixer or cashed out are lower urgency
Amount involvedLarger victim losses can be weighted higher
Match confidenceA wallet already traced to a known exchange is immediately actionable and should jump the queue
Time since complaint filedFresh complaints on still-traceable funds are the most time-critical — crypto moves fast
Pattern match to an active campaignA wallet whose fingerprint matches several other recent complaints suggests an active fraud ring, not an isolated case

Output for investigators: a ranked queue — High priority (large loss, still traceable, matches an active pattern) / Medium / Low (already cold, small amount) — instead of a flat, unordered complaint list. This reuses the same fingerprint-matching engine from Pattern Detection, so it adds real capability without a separate system.

12 · Scrutiny & Watch-Outs

What to get right before demo day

Honest issues found while building this document, plus real patterns from past SIH judging — read this as a team before finalizing anything.

Hardcoded demos get caught

Judges explicitly test with inputs you didn't prepare for. A tiny label list means most real addresses will show "no match" — expand it meaningfully before demo day, and make sure the heuristic fallback genuinely fires so "no match" is rare, not the default outcome.

Feasibility is scored explicitly

Judges reward a narrow, deeply understood problem executed well over an ambitious one the team can't fully run live. Know exactly which features are real code vs. described roadmap, and never blur that line under questioning.

Internal consistency matters

Don't let two different slides/sections describe the same feature two different ways (this happened once already in an earlier draft of this doc — the "laundering wallet detection" row existed twice with different answers). Proofread the final PPT as one team, out loud, end to end.

Keep the architecture diagram in sync

If you add or cut a feature, update the diagram same day. A diagram that doesn't match what you say out loud is an easy, avoidable point of confusion for judges.

Clarity beats jargon

Judges read many submissions quickly. A simply explained idea beats a technically dense one that's hard to follow in five minutes — lead with the plain-English version, keep technical depth for Q&A.

Mixers are a real, defensible dead end

Don't overclaim full traceability. State clearly that sanctioned mixers are cryptographically unlinkable beyond a point — this is true even for commercial tools, and saying so proactively builds credibility rather than losing points.
